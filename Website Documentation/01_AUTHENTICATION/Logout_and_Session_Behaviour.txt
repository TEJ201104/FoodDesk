1. FEATURE OVERVIEW
--------------------------------------------------------------------------------
Logout and Session Behaviour governs the complete lifecycle of user authentication in FoodDesk, from initial session establishment and browser persistence to runtime state hydration, multi-tab synchronization, and safe session termination (logout).

Because FoodDesk is designed as a high-speed, local-first commercial point of sale application, session persistence must be robust: counter staff cannot have their screens lock or lose active data due to an accidental browser refresh or brief network drop. At the same time, when staff finish their shift or hand over the counter terminal, clicking Logout must cleanly purge authentication tokens, reset in-memory contexts, and transition the terminal to a clean login state without corrupting stored orders, sales history, or stall configurations.


2. HOW TO ACCESS
--------------------------------------------------------------------------------
- Logout Action Button: Located in the top-right corner of the persistent Navbar across all protected pages.
- Programmatic Trigger: Triggered automatically by StallGuard or RoleGuard if a corrupted, invalid, or zero-stall session is detected upon page mount.


3. SCREEN LAYOUT

B. SESSION STORAGE KEYS IN BROWSER:
- 'fooddesk_session':
  - Storage Location: window.localStorage.
  - Data Structure: JSON string containing:
    - user: { id, email, name, role, authorizedStalls }
    - activeStall: { id, name, slug, category, address, operatingHours, paymentSettings }
    - token: Mock JWT bearer token (e.g., 'mock-jwt-token-stall_owner-...')
    - expiresAt: Epoch millisecond timestamp.
  - Purpose: Primary session container read on application startup.
- 'fooddesk_active_stall_id':
  - Storage Location: window.localStorage.
  - Purpose: Secondary convenience anchor for fast workspace hydration.


5. AVAILABLE ACTIONS
--------------------------------------------------------------------------------
1. Manual Shift Logout:
   Click the "Logout" button in the top navigation bar at any time to end your shift.
2. Cross-Tab Session Clearing:
   Logging out in one browser tab automatically signals all other open FoodDesk tabs via the storage event, causing them to rehydrate or redirect cleanly.
3. Reload & Rehydration:
   Refreshing the browser (F5 or Ctrl+R) does NOT log the user out. The application automatically rehydrates the authenticated session and active stall within 5 milliseconds.


6. STEP-BY-STEP USAGE GUIDE
--------------------------------------------------------------------------------
SCENARIO A: NORMAL SHIFT HANDOVER / LOGOUT
1. At the end of your shift, verify that any active order at the POS counter has been completed or cleared.
2. In the top-right corner of the screen, click the "Logout" button.
3. The application immediately executes:
   - Purges 'fooddesk_session' from browser storage.
   - Sets in-memory AuthContext user and session to null.
   - Clears active stall state.
4. A blue informational toast appears in the top-right corner: "Logged out successfully."
5. The browser transitions immediately to http://localhost:5173/login.
6. The POS terminal is now locked and ready for the next shift operator to log in.

SCENARIO B: ACCIDENTAL BROWSER REFRESH (SESSION RESILIENCE)
1. While managing orders on /orders or preparing items on /kds, press Ctrl+R (or F5) to refresh the page.
2. Notice that you are NOT kicked out to the login screen.
3. AuthProvider executes its startup useEffect, reads the intact 'fooddesk_session' from localStorage, restores the active stall profile, and displays your page exactly as you left it.


7. SYSTEM BEHAVIOUR
--------------------------------------------------------------------------------
- Logout Execution Routine (mockAuthService.logout):
  1. Calls window.localStorage.removeItem('fooddesk_session').
  2. Calls window.localStorage.removeItem('fooddesk_active_stall_id').
  3. Dispatches a custom event or triggers storage event synchronization.
- AuthContext State Synchronization:
  AuthContext's logout callback executes mockAuthService.logout() and sets setSession(null).
- Navigation Enforcement:
  navigate('/login', { replace: true }) replaces the current history entry, preventing the user from clicking the browser's "Back" button to return to authenticated screens.
- Data Preservation:
  CRITICAL: Logging out clears ONLY the user session. It does NOT delete or reset orders (fooddesk_orders), payments (fooddesk_payments), menu catalogs (fooddesk_menu), inventory records (fooddesk_inventory), or expenses (fooddesk_expenses). All business records remain 100% intact.


8. EXPECTED RESULTS

10. RESTRICTIONS AND IMPORTANT NOTES
--------------------------------------------------------------------------------
- Browser LocalStorage Scope:
  In this prototype release, sessions are stored in the browser profile's localStorage. Opening FoodDesk in an Incognito / Private window creates an independent session sandbox that does not share state with the standard browser profile.
- Single Terminal Sharing:
  If multiple counter staff share the same computer terminal, staff MUST click Logout between shifts. Closing the browser tab without logging out leaves the session active in storage until explicitly logged out or cleared.
- Multi-Tab Behavior:
  If a user logs out in Tab A while Tab B is open to /kds, Tab B remains visible until the user interacts or navigates, at which point AuthGuard intercepts the missing session and redirects Tab B to /login.


11. FREQUENTLY ASKED QUESTIONS (FAQ)
--------------------------------------------------------------------------------
Q1: If I log out, will my stall's sales figures, orders, and expenses be deleted?
A1: Absolutely not. FoodDesk stores operational business data separately from session authentication data. Logging out only deletes your active login token. All orders, sales figures, inventory items, and expenses remain safely stored.

Q2: Can someone click the browser "Back" button after I logout to see my stall data?
A2: No. The logout routine uses navigate('/login', { replace: true }), which purges the dashboard from the browser's immediate history stack. If someone attempts to press Back, AuthGuard detects that the session token is missing and immediately forces the browser back to /login.

Q3: Does the session automatically expire after a period of inactivity?
A3: In the demonstration release candidate, the mock JWT token persists in localStorage across browser sessions so that counter demonstrations are not interrupted by unexpected timeouts. In production deployments with remote backends, standard JWT expiry and refresh tokens are enforced.

Q4: How do I completely wipe all demo data and start fresh?
A4: You can reset all demo data to pristine factory seed conditions at any time by logging in as Super Admin (admin@gmail.com / admin), opening Platform Settings (/admin/settings), and executing the typed confirmation reset.

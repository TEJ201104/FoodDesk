1. FEATURE OVERVIEW
--------------------------------------------------------------------------------
This document provides a deep-dive technical specification of data flow, state management, storage keys, and information sharing mechanisms across the FoodDesk platform.

FoodDesk employs a reactive, local-first single-page application (SPA) architecture. To achieve sub-5ms counter responsiveness and high fault tolerance during peak footfall periods, FoodDesk eliminates traditional remote database network latency by maintaining its operational database directly inside the browser's persistent storage engine, coordinated by dedicated services, React Context providers, and custom event buses.

This specification details:
- Storage Keys & Schema definitions in window.localStorage.
- React Context State Providers (AuthContext, StallContext, NotificationContext).
- Service Layer Abstraction (storageService, stallDataService, analyticsService, adminService).
- Cross-Component and Cross-Tab Event Synchronization.
- Safe Mutation Locking via the Web Locks API.


2. HOW TO ACCESS

3. ARCHITECTURAL TOPOLOGY & DATA PIPELINE
--------------------------------------------------------------------------------
Data flow in FoodDesk follows a strictly structured 4-tier pipeline:

[ BROWSER LOCALSTORAGE ]  (Persistent Storage Engine: fooddesk_* keys)
          ▲
          │ (Read / Write via storageService.js & Web Locks)
[ SERVICE LAYER ABSTRACTION ]
  ├── mockAuthService.js   (Authentication, tokens, sessions)
  ├── stallDataService.js  (POS, orders, KDS, menu, inventory, expenses)
  ├── analyticsService.js  (Integer paise P&L calculations, CSV engine)
  └── adminService.js      (Platform GMV, approvals, support tickets)
          ▲
          │ (Reactive Hooks & Context State)
[ REACT CONTEXT PROVIDERS ]
  ├── AuthContext.jsx         (User identity, roles, JWT token)
  ├── StallContext.jsx        (Active stall profile, switcher, cache keys)
  └── NotificationContext.jsx (Global toasts, counter sound synthesizer)
          ▲
          │ (View Binding & Event Dispatchers)
[ USER INTERFACE COMPONENTS & PAGES ]
  (Dashboard, POS, Orders, KDS, Menu, Inventory, Expenses, Analytics, etc.)


4. DETAILED ELEMENT-BY-ELEMENT STORAGE SCHEMA & KEYS
--------------------------------------------------------------------------------
All application data is persisted under namespaced keys prefixed with 'fooddesk_':

1. 'fooddesk_session':
   - Data Schema: Object containing:
     - user: { id, email, name, role, authorizedStalls: [] }
     - activeStall: { id, name, slug, category, address, operatingHours, paymentSettings }
     - token: Bearer string (e.g., 'mock-jwt-token-stall_owner-...')
     - expiresAt: Epoch millisecond timestamp.
   - Lifetime: Persists across browser refreshes until explicit Logout or Demo Reset.

2. 'fooddesk_stalls':
   - Data Schema: Array of stall objects (stall-1 Fast Food, stall-2 Beverages, stall-3 Desserts).
   - Contains: id, name, slug, category, description, address, operatingHours, paymentSettings, status.

3. 'fooddesk_menu':
   - Data Schema: Array of menu item objects.
   - Contains: id, stallId, name, category, sellingPrice, costPrice (COGS), description, isVeg, isAvailable, isArchived, imageUrl.

4. 'fooddesk_orders':
   - Data Schema: Array of order records.
   - Contains: id (UUID), stallId, orderNumber (ORD-YYYYMMDD-XXXX), pickupToken (101-999), items: [ { id, name, category, sellingPrice, costPrice, quantity } ], customerMobile, customerNotes, orderStatus, paymentStatus, paymentMethod, financials: { subtotal, discountType, discountValue, discountAmount, grandTotal, totalCostOfGoodsSold }, createdAt.

5. 'fooddesk_payments':
   - Data Schema: Array of payment ledger transactions.
   - Contains: id, stallId, orderId, amount, method ('cash' | 'upi'), status ('successful' | 'refunded'), timestamp, referenceId.

6. 'fooddesk_expenses':
   - Data Schema: Array of operational expense records.
   - Contains: id, stallId, date, category, amount, description, recordedBy, isDeleted, auditTrail: [ { version, amount, category, modifiedBy, timestamp } ].

7. 'fooddesk_inventory':
   - Data Schema: Array of raw material ingredient records.
   - Contains: id, stallId, name, currentStock, minThreshold, unit, status, description, updatedAt.

8. 'fooddesk_stock_movements':
   - Data Schema: Array of stock transaction records.
   - Contains: id, stallId, ingredientId, ingredientName, type ('initial' | 'add' | 'reduce' | 'wastage'), quantityChanged, previousQuantity, newQuantity, unit, reason, notes, user, timestamp.

9. 'fooddesk_tickets':
   - Data Schema: Array of help desk support tickets.
   - Contains: id (TKT-XXX), stallId, stallName, ownerId, ownerName, title, category, priority, status, description, messages: [ { id, text, authorName, authorRole, timestamp } ], resolutionNote, resolvedAt, submittedAt, history: [].

10. 'fooddesk_admin_activity':
    - Data Schema: Chronological log of administrative actions.

6. STEP-BY-STEP DATA FLOW TRACE
--------------------------------------------------------------------------------
TRACING AN ORDER TRANSACTION THROUGH THE COMPLETE SYSTEM:

1. TRIGGER (POS Page):
   Cashier clicks "Confirm & Dispatch Order" on the Review Modal.

2. SERVICE EXECUTION (stallDataService.createOrder):
   - Computes sequential order number: ORD-20261116-0001.
   - Computes sequential pickup token: #101.
   - Freezes immutable item snapshots: Clones sellingPrice (₹120) and costPrice (₹50).
   - Computes integer paise totals: subtotal = ₹240.00, grandTotal = ₹240.00, totalCOGS = ₹100.00.
   - Saves record to 'fooddesk_orders' in localStorage via storageService.

3. CONTEXT & STORAGE NOTIFICATION:
   - Dispatches DOM CustomEvent: 'fooddesk:order-created' with order detail payload.
   - Browser fires native 'storage' event.

4. MULTI-MODULE SIMULTANEOUS REACTION:
   - KDS (Module 6): Catches 'fooddesk:order-created'. Plays audio bell chime. Renders Card #101 in "Received" column.
   - Order History (Module 7): Catches 'fooddesk:order-created'. Adds row to orders table with green "LATEST" badge.
   - Financial Analytics (Module 11): When payment is recorded, adds ₹240.00 to Gross Sales and freezes ₹100.00 in COGS.
   - Customer Tracker (Module 13): When customer navigates to /track/fast-food-stall/ORD-20261116-0001, tracker reflects "Step 1: Order Received" with Token #101.


7. SYSTEM BEHAVIOUR & CONCURRENCY
--------------------------------------------------------------------------------
- Web Locks API Coordination:
  In browsers supporting the W3C Web Locks API (navigator.locks), critical write operations acquire an exclusive lock:
  navigator.locks.request('fooddesk_data_lock', async () => { ... }).
  This prevents two browser tabs from attempting to write or allocate the same sequential token simultaneously.
- Reactivity without Polling:
  FoodDesk NEVER runs polling setInterval loops to check for new orders. The architecture is strictly reactive and event-driven, resulting in 0% CPU idle usage and instant response times.
- Client-Side Tamper Recovery (StallGuard):
  If localStorage.fooddesk_session is tampered with via DevTools, StallGuard detects that activeStall is unauthorized and executes recoverAuthorizedStall(), restoring the session to the primary authorized stall automatically.

10. RESTRICTIONS AND IMPORTANT NOTES
--------------------------------------------------------------------------------
- LocalStorage Storage Ceiling:
  Modern web browsers allocate between 5MB and 10MB of storage per origin for localStorage. In FoodDesk, 5MB accommodates more than 15,000 complete order tickets and 10,000 expense records—far exceeding typical demo and daily operational requirements.
- Browser Cache Clearing:
  Manually clearing the browser's cookies and site data will wipe the localStorage keys. FoodDesk can be immediately restored to factory seed state at any time via the Super Admin demo reset or automatic initial re-seeding on fresh launch.


11. FREQUENTLY ASKED QUESTIONS (FAQ)
--------------------------------------------------------------------------------
Q1: Can data from Stall 1 overwrite data in Stall 2?
A1: No. While all orders live in the shared 'fooddesk_orders' array, every order record contains an immutable stallId property. The service layer strictly filters every query by stallId, guaranteeing absolute data isolation.

Q2: What happens if the computer crashes while an order is being placed?
A2: Order records are written to localStorage synchronously before any UI success screens or print modals appear. If the computer loses power, the order is already safely committed to disk.

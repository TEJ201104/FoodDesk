1. FEATURE OVERVIEW
--------------------------------------------------------------------------------
This document provides a comprehensive structural architectural overview of how all thirteen functional modules in FoodDesk connect, interact, and collaborate as an integrated enterprise ecosystem.

FoodDesk is not an assortment of disjointed web pages; it is a unified, event-driven single-page application where an action performed in one module (such as checking out a customer order in POS) instantaneously radiates state updates across the entire application:
- Assigns a sequential token and creates an immutable order ticket in Order Management.
- Alerts kitchen cooks with an audio bell and updates the live cooking Kanban on the Kitchen Display System (KDS).
- Advances the live progress stepper on the customer's personal mobile phone tracking screen.
- Freezes item cost snapshots and recalculates Gross Sales, COGS, and Net Profit in Financial Analytics.
- Updates daily operational queue counts and revenue cards on the Stall Dashboard.

All of this occurs with zero server round-trip latency using a local-first browser storage and event synchronization architecture.

3. SYSTEM TOPOLOGY & MODULE HIERARCHY
--------------------------------------------------------------------------------
The FoodDesk platform is organized into three architectural layers:

LAYER 1: FOUNDATIONAL PLATFORM SERVICES (CORE INFRASTRUCTURE)
- Module 1: Authentication & Identity Gate (mockAuthService, AuthContext, initialUsers).
- Module 2: Application Shell Layout (AppLayout, Navbar, Sidebar).
- Module 3: Multi-Stall Data Isolation Engine (StallContext, StallGuard, stallDataService, storageService).

LAYER 2: STALL OPERATIONAL WORKSTATIONS (FRONT-OF-HOUSE & BACK-OF-HOUSE)
- Module 4: Counter Point of Sale (POS) Workstation.
- Module 5: Payment Processing & Digital Thermal Receipts.
- Module 6: Real-Time Kitchen Display System (KDS).
- Module 7: Order Management Hub & Reprint Station.
- Module 8: Menu Catalog & Pricing Management.
- Module 9: Inventory & Ingredient Stock Tracking.
- Module 10: Expense Management & Operating Costs.
- Module 11: Financial Analytics & Profit/Loss Engine.

LAYER 3: GOVERNANCE & PUBLIC INTERFACES
- Module 12: Super Admin Governance Portal (Stalls, Owners, Support Tickets, Settings).
- Module 13: Public Customer Digital Menu & Order Tracking Portals.


4. DETAILED ELEMENT-BY-ELEMENT INTER-MODULE DEPENDENCY MAP
--------------------------------------------------------------------------------
Below is the explicit dependency matrix illustrating how each module consumes and provides data:

A. AUTHENTICATION & SESSION (MODULES 1 & 2):
- Feeds: All protected routes with authenticated user identity, role, and authorized stalls array.
- Interacts With: Module 3 (Stall Context) to lock the active workspace.
- Enforces: Route protection via AuthGuard and role separation via RoleGuard.

B. MULTI-STALL ISOLATION ENGINE (MODULE 3):
- Providers: StallContext, StallGuard, stallDataService.
- Consumer Dependencies: Modules 4, 5, 6, 7, 8, 9, 10, 11, and 13 all depend on currentStall.id to parameterize their queries.
- Guarantees: Complete data segregation between Fast Food (stall-1), Beverages (stall-2), and Desserts (stall-3).

C. POINT OF SALE (MODULE 4) & PAYMENTS (MODULE 5):
- Consumes: Menu items from Module 8 (Menu Management).
- Consumes: Payment configuration (UPI VPA, Cash allowed) from Module 3 (Stall Settings).
- Emits: New order tickets to Module 7 (Order History).
- Emits: Kitchen preparation cards to Module 6 (Kitchen Display System).
- Emits: Realized sales revenue and snapshot COGS to Module 11 (Financial Analytics).
- Emits: Live milestone updates to Module 13 (Customer Tracking).

D. KITCHEN DISPLAY SYSTEM (MODULE 6):
- Consumes: Active orders dispatched from Module 4 (POS).
- Modifies: orderStatus (received → preparing → ready → completed).
- Dispatches: 'fooddesk:order-status-updated' events.
- Synchronizes With: Module 7 (Order Management reflects status badges) and Module 13 (Customer tracker reflects live progress).

E. ORDER MANAGEMENT HUB (MODULE 7):
- Aggregates: All orders created by Module 4.
- Executes: Sensitive cancellations and simulated refunds.
- Synchronizes With: Module 11 (Financial Analytics subtracts refunds from net revenue).
- Re-triggers: Thermal receipt generation (Module 5).

F. MENU MANAGEMENT (MODULE 8):
- Manages: Item names, categories, selling prices, cost baselines (COGS), and stock availability flags.
- Feeds: Module 4 (POS menu grid) and Module 13 (Public customer menu).
- Emits: 'fooddesk:menu_updated' events when stock availability is toggled.

G. INVENTORY (MODULE 9) & EXPENSES (MODULE 10):
- Module 9 tracks: Physical stock balances, units, thresholds, and wastage logs.
- Module 10 tracks: Financial cash outflows for raw materials, utilities, labor, and maintenance.
- Feeds: Module 11 (Financial Analytics consumes total expenses for net profit calculation).
- Feeds: Module 2 (Dashboard displays today's expenses and restock alert counts).

H. FINANCIAL ANALYTICS (MODULE 11):
- Aggregates: Paid orders from Module 7, snapshot COGS from Module 4/8, and operating expenses from Module 10.
- Computes: Authoritative P&L statements across flexible date presets.
- Feeds: Executive summary cards on Module 2 (Stall Dashboard).

I. SUPER ADMIN GOVERNANCE (MODULE 12):
- Supervises: All stalls (Module 3), all owners (Module 1), and centralized support tickets (Module 11).
- Controls: Factory demo data reset across all local storage collections.

J. PUBLIC CUSTOMER PORTALS (MODULE 13):
- Public Digital Menu consumes active catalog items from Module 8 (stripping COGS).
- Customer Order Tracker consumes live milestone updates from Module 6 (KDS).

7. SYSTEM BEHAVIOUR
--------------------------------------------------------------------------------
- Decoupled Event-Driven Communication:
  Modules do not import or call each other directly; they communicate via standard DOM custom event dispatchers on window:
  - 'fooddesk:order-created'
  - 'fooddesk:order-status-updated'
  - 'fooddesk:payment-completed'
  - 'fooddesk:menu_updated'
  - 'fooddesk:categories_updated'
  - 'storage' (for multi-tab/cross-window synchronization).
- Immutable Snapshot COGS Preservation:
  When an order is created, item.costPrice is deeply cloned into order.items. Even if the owner changes item costs in Module 8 ten minutes later, Module 11's historical COGS calculations remain 100% stable.

10. RESTRICTIONS AND IMPORTANT NOTES
--------------------------------------------------------------------------------
- Single Source of Truth:
  window.localStorage (abstracted through storageService.js) serves as the persistent database. All modules read and write to this shared local store.
- Browser Storage Scope:
  All cross-module synchronization operates within the active browser profile. Incognito tabs or different web browsers operate in isolated sandboxes.


11. FREQUENTLY ASKED QUESTIONS (FAQ)
--------------------------------------------------------------------------------
Q1: If the POS crashes or the browser tab closes, will the kitchen lose the order?
A1: No! The order is committed to localStorage before the POS success screen appears. The KDS reads directly from storage and retains the ticket.

Q2: How do customer phones receive live updates without a websocket server?
A2: In the local-first prototype release, cross-tab DOM storage events synchronize screens on the same browser/device network. In production cloud deployments, a lightweight WebSocket or Server-Sent Events (SSE) gateway handles multi-device relay.

1. FEATURE OVERVIEW
--------------------------------------------------------------------------------
This document establishes a transparent, rigorous, and exhaustive audit record of the known operational characteristics, architectural boundaries, deliberate prototype simplifications, and production roadmap considerations of the FoodDesk frontend release candidate build.

FoodDesk was engineered as a high-fidelity frontend commercial prototype implementing all eleven core functional modules defined in the Master Project Requirements Document (PRD) and Frontend Implementation Plan. While it provides 100% realistic, interactive, and mathematically sound operational workflows across POS ordering, kitchen display expedition, inventory tracking, operating expenses, financial analytics, and super admin governance, it deliberately utilizes browser-native persistence and simulated external integrations rather than live cloud backend infrastructure.

Understanding these deliberate architectural choices is essential for accurate evaluation, demonstration, and future production deployment planning.

3. ARCHITECTURAL BOUNDARIES & SCOPE
--------------------------------------------------------------------------------
The application operates within four fundamental architectural boundaries:
1. Storage Boundary: Client-side persistent localStorage with service-layer abstraction.
2. Network Boundary: Single-origin browser execution without external HTTP API dependencies.
3. Concurrency Boundary: Multi-tab synchronization within the same browser profile via DOM events and Web Locks API.
4. Security Boundary: Client-side RBAC and tamper recovery (StallGuard), suitable for demonstration and local counter operation.


4. DETAILED ELEMENT-BY-ELEMENT PROTOTYPE CHARACTERISTICS
--------------------------------------------------------------------------------
Every known limitation, prototype simplification, and operational constraint is cataloged in full detail below:

A. PERSISTENCE ENGINE & STORAGE CAPACITY (LOCALSTORAGE):
- Current Implementation:
  All application datasets (stalls, users, menu items, order queues, payment transactions, expenses, inventory items, stock movements, and support tickets) are serialized into JSON strings and stored in the browser's window.localStorage.
- Storage Ceiling:
  Standard desktop browsers (Chrome, Edge, Safari, Firefox) allocate 5MB of storage per origin. In FoodDesk, 5MB accommodates approximately 15,000 complete order tickets and 10,000 expense records.
- Production Roadmap:
  For multi-year enterprise operations, the service layer abstraction (storageService.js) is designed to be cleanly swapped with an asynchronous REST/GraphQL client connected to a PostgreSQL or Supabase backend.

B. BROWSER PROFILE SANDBOXING:
- Current Implementation:
  Data is stored within the specific browser user profile. If a user opens FoodDesk in an Incognito / Private window, or switches from Google Chrome to Microsoft Edge, each browser profile maintains its own independent storage sandbox.
- Production Roadmap:
  Centralized cloud databases will allow disparate physical devices (e.g., a counter tablet and a separate kitchen tablet) to communicate across separate physical networks.

C. SIMULATED PAYMENT GATEWAYS:
- Current Implementation:
  When a customer pays via UPI, the system renders a cryptographically compliant dynamic Bharat QR code encoding the exact rupee amount and stall VPA. However, bank settlement confirmation is simulated via user confirmation ("Verify & Confirm UPI Payment") rather than receiving an automated webhook notification from Razorpay, Cashfree, or NPCI.
- Production Roadmap:
  In production, a webhook listener microservice will listen for live NPCI bank callbacks and automatically advance payment status from Pending to Paid.

D. NO AUTOMATIC INVENTORY SALES DEDUCTION:
- Current Implementation:
  In strict accordance with PRD Section 9, placing an order at the POS counter does NOT automatically decrement raw ingredients (buns, patties, cooking oil) from the inventory ledger. Raw materials are tracked manually via periodic physical stock takes, manual stock adjustments, and wastage incident logs.
- Rationale:
  In commercial food stalls, recipe yield variability, ingredient substitutions, and batch cooking create significant recipe drift. Manual tracking prevents erroneous automated stockouts.
- Production Roadmap:
  Future enterprise builds will introduce an optional automated Bill of Materials (BOM) / recipe deduction engine for standardized franchise stalls.

E. CLIENT-SIDE TAMPER DETECTION (STALLGUARD):
- Current Implementation:
  StallGuard (StallGuard.jsx) monitors localStorage for direct DevTools edits to the active stall session and automatically recovers to the primary authorized stall. While effective for frontend demonstration resilience, client-side security cannot replace server-side token signature verification.
- Production Roadmap:
  Production deployments will enforce cryptographically signed JWT tokens with server-side HMAC-SHA256 verification and HTTP-only cookies.

F. SIMULATED PRINTER OUTPUT:
- Current Implementation:
  The Digital Thermal Receipt modal outputs via the browser's native window.print() API using custom CSS media print rules formatted for 58mm/80mm widths.
- Production Roadmap:
  Direct ESC/POS raw socket printing via WebUSB or WebBluetooth for zero-dialogue, silent, high-speed thermal printing directly from the POS interface.

7. SYSTEM BEHAVIOUR
--------------------------------------------------------------------------------
- Zero Server Failure Risk:
  Because the prototype executes locally in the browser, demonstrations are immune to cloud server crashes, API rate limits, external gateway outages, or internet connectivity drops.
- Fault-Tolerant Re-Seeding:
  If a tester accidentally clears their browser storage, storageService.init() automatically detects the missing collections and re-seeds all 3 stalls, 30 menu items, baseline orders, and support tickets within 5 milliseconds.

11. FREQUENTLY ASKED QUESTIONS (FAQ)
--------------------------------------------------------------------------------
Q1: Can FoodDesk be used in a real food stall right now?
A1: Yes! For a single counter workstation with an attached USB thermal printer, FoodDesk can be used immediately for counter ordering, cash calculation, thermal receipts, and daily P&L tracking.

Q2: How difficult is it to migrate this prototype to a cloud backend?
A2: Extremely straightforward. The codebase strictly separates UI components from data persistence via dedicated service files (stallDataService.js, analyticsService.js, adminService.js, storageService.js). Replacing the localStorage calls inside storageService.js with fetch() or Axios calls connects the entire frontend to a cloud backend with zero component rewriting!

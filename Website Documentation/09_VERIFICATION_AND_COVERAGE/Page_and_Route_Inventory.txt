1. FEATURE OVERVIEW
--------------------------------------------------------------------------------
This document provides an exhaustive, definitive inventory of every client-side page, URL path, route guard, layout wrapper, URL parameter, access tier, and fallback rule implemented in the FoodDesk application.

FoodDesk's client-side routing is architected using React Router DOM (v6.22.0) and centralized inside frontend/src/routes/AppRoutes.jsx. The architecture incorporates a strict multi-layer defense-in-depth routing strategy designed to guarantee tenant isolation, prevent unauthorized privilege escalation, enforce session validity, and provide seamless customer-facing public access.

Key Routing Characteristics:
- Total Route Entries: 18 distinct route definitions + 1 root redirect + 1 wildcard catch-all redirect.
- Access Tiers: Public Customer Tier (3 routes), Public Authentication Tier (1 route), Protected Stall Owner Tier (10 routes), Protected Super Admin Tier (5 routes).
- Multi-Layer Protection: AuthGuard (session existence), RoleGuard (RBAC role matching), StallGuard (tenant workspace ownership & anti-tamper recovery), PublicAuthRoute (prevents authenticated users from re-accessing login).
- Workspace Decoupling: Operational stall routes dynamically bind to StallContext, isolating localStorage keys and memory spaces per stall.

3. SCREEN LAYOUT & ROUTING ARCHITECTURE
--------------------------------------------------------------------------------
The route hierarchy is structured into three fundamental zones:

ZONE A: PUBLIC UNGUARDED ZONE
- Completely open routes accessible by any internet visitor or smartphone diner scanning a QR code.
- Does not render AppLayout (no admin navbar, no sidebar, no operational controls).
- Renders lightweight, customer-optimized, high-performance layouts.

ZONE B: PUBLIC AUTHENTICATION GATE
- Wrapped in PublicAuthRoute.
- If an unauthenticated user visits /login, renders LoginPage.
- If an already authenticated user visits /login, automatically redirects them to their respective operational dashboard (/dashboard for Stall Owners, /admin/dashboard for Super Admins).

ZONE C: PROTECTED OPERATIONAL WORKSPACE (AppLayout)
- Wrapped in AuthGuard (checks user existence and token validity).
- Renders the global AppLayout (sticky top Navbar, dynamic collapsible Sidebar, responsive mobile drawer, and main content <Outlet />).
- Subdivided by RoleGuard:
  * 'stall_owner': Further wrapped by StallGuard, granting access to 10 stall operations pages.
  * 'super_admin': Grants access to 5 global governance and administration pages.

5. AVAILABLE ACTIONS & ROUTE TRANSITIONS
--------------------------------------------------------------------------------
The following transition rules govern movement between routes:

1. Unauthenticated Visitor Navigation:
   - Allowed Paths: /login, /menu/:stallSlug, /track/:stallSlug, /track/:stallSlug/:orderNumber.
   - Any attempt to visit protected paths (/dashboard, /pos, /admin/...) triggers AuthGuard, immediately redirecting to /login with state={{ from: location }} preserved.

2. Stall Owner Navigation:
   - Sidebar links allow seamless switching among all 10 stall routes (/dashboard, /pos, /orders, /kds, /menu, /expenses, /analytics, /inventory, /support, /settings).
   - Any attempt to enter /admin/* paths triggers RoleGuard, which detects a role mismatch (user role: 'stall_owner' vs required role: 'super_admin') and immediately bounces the user back to /dashboard.
   - Active stall workspace switching (via the Navbar stall dropdown) maintains the current operational route (e.g. staying on /pos) while updating the active stall context and re-fetching data.

3. Super Admin Navigation:
   - Sidebar links allow navigation across the 5 admin routes (/admin/dashboard, /admin/stalls, /admin/owners, /admin/tickets, /admin/settings).
   - Any attempt to enter stall operational routes (/pos, /kds, /inventory) triggers RoleGuard, intercepting the request and redirecting to /admin/dashboard.

4. Customer QR-Code Flow:
   - Scanning a table QR code opens /menu/:stallSlug.
   - Viewing an order opens /track/:stallSlug/:orderNumber.
   - Customers have no access to admin or stall owner controls; the customer interface contains no links to internal routes.

7. SYSTEM BEHAVIOUR & ROUTING LIFECYCLE
--------------------------------------------------------------------------------
When a URL transition is initiated, FoodDesk executes a strict, 5-phase evaluation pipeline:

PHASE 1: URL Matching
- React Router matches the requested path against the AppRoutes declaration tree.
- If no route matches, Route 21 (*) captures the request and routes to Phase 5.

PHASE 2: AuthGuard Evaluation
- If the route is inside the protected layout wrapper, AuthGuard checks AuthContext.isAuthenticated.
- If isAuthenticated === false, navigation is aborted, and <Navigate to="/login" state={{ from: location }} replace /> is triggered.

PHASE 3: RoleGuard Evaluation
- RoleGuard inspects user.role against the route's allowedRoles array.
- If the current role is not in allowedRoles, RoleGuard cancels mounting and redirects:
  * Super Admin attempting stall route -> Redirected to /admin/dashboard.
  * Stall Owner attempting admin route -> Redirected to /dashboard.

PHASE 4: StallGuard Evaluation (Stall Owner Routes Only)
- StallGuard checks activeStall against user.authorizedStalls.
- If valid, renders <Outlet />.
- If invalid or tampered with in localStorage, StallGuard invokes recoverAuthorizedStall(), displays a warning toast, and safely rebinds to the user's primary authorized stall.

PHASE 5: Component Mount & Data Rehydration
- The targeted page component mounts.
- It pulls activeStall from StallContext and loads the corresponding data from localStorage or mock services.

10. RESTRICTIONS AND IMPORTANT NOTES
--------------------------------------------------------------------------------
1. No Mixed-Role Users: A user cannot simultaneously be a stall_owner and a super_admin. Role privileges are strictly partitioned.
2. Direct URL Entry: Pasting deep URLs (e.g., /pos or /admin/stalls) directly into the browser address bar is fully supported; guards execute before rendering any child component.
3. Fallback Redirection: Any unauthenticated request to an invalid URL safely falls back to /login rather than throwing an unhandled client error.
4. Slug Resolution: Public menu slugs are matched case-insensitively against registered stall records.


11. FREQUENTLY ASKED QUESTIONS
--------------------------------------------------------------------------------
Q1: What happens if an unauthenticated user tries to visit /pos directly?
A1: AuthGuard intercepts the request before POSPage mounts, redirecting the user to /login and remembering /pos in navigation state so they can be returned after login.

Q2: Can a Stall Owner access the Super Admin Dashboard at /admin/dashboard?
A2: No. RoleGuard detects that user.role ('stall_owner') is not in ['super_admin'] and automatically redirects them to /dashboard.

Q3: Can a customer access internal stall pages from the public menu?
A3: No. The public menu layout is completely decoupled from AppLayout and contains no navigation links or tokens to internal routes.

Q4: What happens if a user navigates to a non-existent URL like /unknown-page?
A4: The wildcard route (*) catches the request and redirects authenticated users to their dashboard, or unauthenticated visitors to /login.
